# Prototype measurements and verification

Measured on 2026-10-20, Linux x64, Node 22.12.0, using the installed dependencies. Timings are single observations in a warm process, not medians, percentiles or a production capacity claim. The synthetic input is generated by DuckDB `range`, with 100,000 repeating grid coordinates and duplicate observations at larger sizes. It does not model remote database latency or arbitrary expensive upstream SQL.

No Chromium/app inspection, screenshots, browser interaction benchmark or Canvas paint benchmark was completed. After the instruction to stop browser work, the attempted browser launch and local browser test server were stopped; the launch had failed in the sandbox. All results below come from non-browser execution. The browser fixture is code for a later authorized validation, not evidence of successful UI behavior.

## Native CLI query pipeline

The bridge calls the existing `Session.Compute`/`Engine.Query` and Arrow IPC encoder. The row-count/result paging check uses `Session.RunQuery` and `QueryResultPage`. A separate Go test exercises the actual protected HTTP compute route, including editor ownership, document ID, origin, Arrow and request cancellation.

Benchmarks use a 600×400 chart-sized layout, 592×268 inner viewport, 502×204 plot, and fixed [0,1] axis domains. At large sizes this gives 62×25 bins. The UI uses automatic domains; these numbers isolate a consistent analytical domain. Query times include DuckDB execution and the existing Go row-to-Arrow construction. IPC serialization is measured separately. Pipe transport, JavaScript decoding and scheduling are included in roundtrip values; they are **not** labelled network transfer.

| Source rows | Representation | Returned marks | Plot query ms | IPC serialization ms | IPC bytes | Exact triangle query ms |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 1,000 | points | 1,000 | 1.91 | 0.08 | 24,480 | 10.26 |
| 10,000 | points | 10,000 | 2.43 | 7.87 | 240,480 | 11.52 |
| 100,000 | density | 1,550 | 10.97 | 0.03 | 37,680 | 21.66 |
| 1,000,000 | density | 1,550 | 73.51 | 0.03 | 37,680 | 71.87 |
| 10,000,000 | density | 1,550 | 676.51 | 0.08 | 37,680 | 455.42 |

The 10,000-row serialization observation is an outlier in this single run; do not generalize it without repeated isolated measurement. Domain/statistics requests took about 28.44 ms at one million and 309.13 ms at ten million rows. The corresponding end-to-end plot roundtrips were 74.28 ms and 677.24 ms; exact triangle roundtrips were 72.65 ms and 456.23 ms. Thus first load includes the statistics scan **plus** the plot scan.

Planning took under 0.2 ms in these cases. Cache hits took approximately 0.01–0.03 ms. Preview membership on 1,550 bin centers took roughly 0.1 ms. These are CPU routines, not visual-feedback latency. The main timing polygon has three edges; a separate 64-edge correctness test exercises a more realistic freehand outline but does not establish a latency distribution.

The ECharts baseline uses the existing result-view paging path and current 10,000-row limit. At one million rows, its page was 240,472 IPC bytes and 10,000 observations; the native plot was 37,680 bytes and represented all one million observations as 1,550 bins. The baseline page query is faster because it does not aggregate the whole input. These displays have different coverage and cannot be compared as equivalent full-data renderings.

## Actual component SVG generation, without a browser

The experiment uses Kavla's `buildChartOption` with ECharts SVG SSR and the native `ScatterMarks` plus `ScatterAxes` with React SSR. ECharts animations are disabled for SSR. It generates strings only: no DOM insertion, SVG layout, Canvas paint, GPU, resize observer, camera interaction or browser frame scheduling is included. The application normally uses Canvas at these counts; **these are not measurements of its default rendering mode**.

| Source rows | Native one-copy SVG ms | ECharts one-copy SVG ms | Native 30-copy SVG ms | ECharts 30-copy SVG ms |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 9.33 | 62.78 | 24.55 | 525.10 |
| 10,000 | 12.90 | 136.83 | 309.44 | 3,875.32 |
| 100,000 | 7.99 | 123.65 | 47.49 | 4,001.13 |
| 1,000,000 | 1.75 | 159.57 | 55.71 | 4,044.00 |

The raw file includes 1, 10 and 30 **sequential string-generation copies**, not 30 visible canvas shapes. Different markup complexity, JIT warmup and reduced native mark counts explain much of the gap. No claim of a comparable browser speedup follows from these timings. The final Node process RSS (~562 MiB) includes both libraries, generated strings and accumulated runtime/GC state; it cannot be attributed to either renderer.

## WASM experiment in Node

The installed WASM reports DuckDB v1.5.4. Its MVP build ran in Node using a single existing connection and Mosaic Core, without a browser, worker or network. A table created before constructing the coordinator remained queryable through the connector, demonstrating database reuse. This does not benchmark a browser worker's scheduling or memory behavior.

| 1,000,000 | 1,550 | 601.66 | 322.76 | 40.00 |

Selected counts match the native run, including 128,010 and 1,280,100 observations. The raw file includes CPU-time deltas and process memory per case. WASM heap capacity is not total process memory or live query allocation. These results support bounded transfer, caching and deliberate source materialization; they do not justify running a second database in the current app.

## Correctness coverage

Both TypeScript configurations and a production Vite build to a temporary output directory passed. The build reports large-chunk warnings. The focused SQL/Mosaic/geometry tests, archive chart compatibility test, protected compute-route test and existing document round-trip/extraction tests passed. No linting or formatting was run.

- **Core acceptance:** 1,000,000 upstream observations, 1,890 density bins at the acceptance test dimensions, 128,010 selected rows. The oracle uses an independent integer inequality. Both directions of `EXCEPT ALL` return zero, then the generated SQL is executed as a result view and pagination reaches rows 128,000–128,009.
- Small exact row sets versus D3's independent polygon routine, with known explicitly included boundaries and duplicate coordinates.
- Self intersections, very thin valid outlines, invalid/collinear outlines, zero-row and single-row results, null/NaN/infinite observations.
- Logarithmic and reversed axes, domain clipping and quoted identifiers.
- A complete 64-edge polygon over a million rows versus an independently computed point oracle.
- Geometry across aspect ratios and movement/rotation coordinate transforms. LOD planning has no input into predicate generation.
- Live selection against changing source rows; source revision keys and uncached authoritative counts.
- Real Mosaic Arrow decode, cache hits, in-flight sharing, per-selection abort forwarding, session cleanup and the installed cancellation limitation.
- Two custom Mosaic clients updated by a shared polygon `Selection`, without a chart library.
- Mosaic M4 extrema/run identities and DuckDB bar grouping/cardinality overflow sentinel.
- Old chart records from the bundled Titanic `.kavla` archive migrate and validate; additive native metadata round-trips through current validators without changing props.
- Protected compute HTTP route retains editor ownership, document isolation, origin checks, Arrow results, cancellation and SELECT-only behavior.

Not completed: the pointer-event-to-new-SQL-shape acceptance path in a real browser, app save/reopen interaction, Canvas-vs-SVG selection interaction, high-DPI screenshots, browser WASM/CPU memory, network throughput, simultaneous visible chart benchmarks, resize/pan/zoom frame latency, and GPU comparison. The architecture excludes renderer state from SQL and tests that separation, but that does not replace a browser integration test.

## Reproduction

No dependency installation or browser is needed for these checks. Build the isolated bridge from `cli/`:

```sh
GOCACHE=/tmp/go-cache go build -o /tmp/kavla-viz-bridge ./internal/vizbench
GOCACHE=/tmp/go-cache go test -vet=off ./internal/localapp -run TestNativeVisualizationComputeUsesProtectedDocumentSession -count=1
```

From `app/`:

```sh
./node_modules/.bin/tsc --noEmit
./node_modules/.bin/tsc --noEmit -p Chart/native/tsconfig.json
node --experimental-transform-types --test --test-force-exit Chart/native/selection.test.ts Chart/native/coordinator.test.ts Chart/native/series-planner.test.ts Chart/native/compatibility.test.ts
node Chart/native/run-node-benchmark.mjs
node --experimental-transform-types Chart/native/wasm-node-benchmark.mjs
```

The archive compatibility test uses Python's standard-library ZIP reader. Some sandbox configurations prohibit Node's synchronous subprocess spawn; run that non-visual test with the environment's approved permissions if necessary. `KAVLA_VIZ_BRIDGE` can override the bridge path.

The benchmark scripts regenerate the JSON files in this directory. `run-node-benchmark.mjs` bundles the actual TSX components into `/tmp/kavla-viz-node`; it does not open or render the app in a browser. `build-harness.mjs` and `browser-harness.tsx` are reserved for a future authorized browser test. Their loopback test transport is intentionally separate from production authentication; the protected-route Go test covers the real HTTP guards. Do not ship or expose the test bridge as an application server.
